**The question: does teaching the input model produce the pairing — a
bridge-band `untilX` together with a `jumpAtX` — and a landing?** Pilot 6
ended with the release value space brushed but never paired.

**The pairing happened — six times, in run B — and the landing still
didn't.** What blocks it now is not the model of the input (run B's seat
planned exactly right: "Arming on freeze with jumpAtX: 645 and untilX:
1150") but the *aim at the lip*: `jumpAtX: 645` was pressed at x=652–656 —
at or past the fall edge — in five of six attempts, so the jump was refused
(`jump-ignored`, `tookOff: false`) and the run walked into the pit. The one
attempt that took off (pressed at 648, `apexY: 363`) carried
`untilX: 1150`, and overflew to `diedAt {884, 571}` — captured, and read
correctly. The sampling bias DESIGN.md documents (a press can land up to
~14px past the requested x, and the driver refuses a jump once airborne) is
now the last blocker standing between a live seat and the bridge: run B
issued `untilX: 720` *with* a jump — the pairing that lands, per the sweep
— and lost it to a press at 656.

Run A is the counterpoint: **its seat never issued a single `jumpAtX`.**
Fifteen minutes, 17 deaths, and every pit approach was a walk-in — it spent
the run trying to *walk* onto the platform (`untilX` 660/670 at the lip,
"land on the platform with untilX=660"), a plan the level geometry refuses
(the bridge stands 47px above the ground; only a jump reaches it). Its
first thought about jump timing arrived at 20:00:08, twelve seconds before
the 429. Same prompt, same teaching, opposite behaviours — one seat
composed the technique line with `jumpAtX`, the other composed it with

## The intercom boundary bug set this pilot's pace

Pilot 6 caught two instances of the wait-start boundary failure. This
pilot ran into it **on almost every coordination cycle of run A** and it
manufactured three of run B's four arm-timeouts:

- Run A's phone spent the run in a metronomic loop: the laptop's ask was
  created 0.4–2.3s before the phone's next `intercom_wait` began, the wait
  ran its full 60s deaf, and the ask arrived only at timeout. Seven waits
  timed out empty this way (19:45:23, 19:46:53, 19:48:26, 19:50:05,
  19:51:20, 19:53:47, 19:57:00), and the laptop's armed moves stood
  waiting through each one: eight arms held 62–84s (`armedForMs` 62649,
  63125, 63668, 64571, 65146, 65876, 69601, 83842) — **every one fired
  eventually, so run A had zero timeouts, but roughly half its 15 minutes
  was seats standing armed while a delivered-but-unseen ask sat in a deaf
  wait.**
- Run B's laptop asks at 20:14:39.677, 20:16:21.755, and 20:18:09.255 were
  created 1.9s, 2.4s, and 3.5s before the phone's next wait began; all
  three waits sat deaf until the *next* message ended them, no fresh
  freeze came, and the laptop's arms timed out at the full 90s
  (`armedForMs` 90045, 90013, 90003). The fourth timeout (20:12:58) was a
  plain cast-before-arm: the freeze completed ~5s before the arm existed.
- One more out-of-order delivery on run A's laptop side: a freeze
  confirmation created 19:52:27.132 was delivered 69.9s late, behind a
  newer message.

The mechanism sharpened by these instances: the failure window is not
strictly "~1s before the wait" — it is **any message the watcher claims
while the recipient is mid-turn**, when the recipient's next action is an
`intercom_wait`. The watcher marks the message seen and queues it as a
steer delivery, which cannot surface until the next LLM call — after the
wait. The 0.4–3.5s pre-wait spread in these runs is just the size of the
mid-turn gap. This makes the fix's locus concrete (the shared `seen` set
between the watcher tick and the wait in `.pi/extensions/intercom/`), and
it is the next scheduled work item.

A quota irony worth stating: the bug is why these were the two longest
runs ever. Standing armed and sitting in deaf waits cost no tokens, so
run A stretched 15 minutes. Fixing the intercom bug will *shorten* live
pilots until the token-rate-429 item lands.

## Findings

1. **The technique line produced the pairing, in one seat of two**
   *(Fact — the pilot's question, half-answered)*. Run B issued
   `jumpAtX` + `untilX` six times — including `untilX: 720`, which cut its
   move mid-air exactly as taught. Run A composed the same teaching with
   walking instead of jumping and never pressed jump once. One prompt line
   does not force the composition; it only makes it available.

2. **The aim at the lip is now the last blocker, and it needs a margin
   taught** *(Fact + Recommendation — prompts, next pilot)*. Six trials at
   `jumpAtX: 645`, five presses at 652–656 (refused), one at 648 (took
   off). The prompt says "just before the edge"; the driver's press lands
   up to ~14px late, and the game refuses airborne presses. One line
   closes it: "set `jumpAtX` at least 20px before the edge you mean to
   leave from — the press can land ~15px late, and a press past the edge
   is refused." With run B's `untilX: 720` already in hand, that line plus
   this pilot's pairing is a landing.

3. **The intercom wait-start bug is no longer an anomaly — it is the
   dominant coordination cost of live pilots** *(Fact — harness)*. ~10 new
   instances across the two runs; it manufactured 3 of run B's 4
   arm-timeouts and put 8 of run A's 12 arms into 60–84s holds. Mechanism
   sharpened: any message claimed by the watcher mid-turn is invisible to
   a wait that starts next. Fix scheduled (BACKLOG item 9).

4. **Every misread lives in the no-record path** *(Fact — item 8's case)*.
   8 invisible deaths this pilot; 3 "crossed the pit/gap" announcements sit
   on top of them, one with a celebratory screenshot. Zero misreads on the
   26 captured deaths. The idle sampler (item 8) is no longer
   observability polish; it is the difference between a seat that can be
   wrong and a seat that cannot check.

5. **The handoff digest injection is per-seat, not per-run** *(Fact — item
   10)*. Run A: phone inherited a digest, laptop clean — the first clean
   seat startup since the extension shipped. Run B: laptop inherited (run
   A's), phone clean. Whatever selects the victim, the chain continues.

6. **No seat has ever written its report when a run ends by 429 or
   ceiling** *(Fact — now 8 seats running)*. Both laptops died mid-plan;
   run A's phone was stopped with the orchestrator, run B's phone idled to
   the kill. The report step exists only in runs that end gracefully,
   which no free-tier run has.

## Honesty caveats

- **Armed moves are driver-reflex**; every crossing rode one. The one
  take-off was freeze-armed.
- **The driver solved every puzzle** (bands consistent with pilots 3–6).
- **No seat wrote a report in either run**; all claims derive from the
  session transcripts, notes files, and intercom stores.
- Run A's orchestrator was hand-stopped 7 minutes after its laptop died;
  its phone's tail (idle waits) is truncated, and nothing else is.
- The aim analysis rests on six trials at a single value (645); no trial
  at a smaller aim exists in this pilot. `diedAt`'s known biases apply.
  `reports/video/20260814-144439/laptop.webm` and
  `reports/video/20260814-151052/laptop.webm` can falsify the mid-fall
  readings (x=680/y=483, x=732/y=529).
