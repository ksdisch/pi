# Constellation co-op pilot, run 9 — planet-1, 2026-08-15

Two runs against constellation `604a422` — the same build pilots 7 and 8 ran, so
the game is unchanged across three pilots. Seats: laptop
`google/gemini-3.5-flash-lite`, phone `google/gemini-3.1-flash-lite`. Four
harness changes shipped into this pilot (PR #37): the **trigger-bound crossing
rule** in the laptop prompt, **`recentDeaths` on `/state`**, the **sampler
keeping its last sample across a death tick**, and a **handoff-digest opt-out**
for seats. Each has its own measurement channel; see "Honesty caveats".

Run A `20260815-055633`: 7m23s of play, 8 deaths, **cleared planet-1**.
Run B `20260815-060414`: 34m46s of play, 49 deaths, no clear, ended by the
2100s orchestrator ceiling.

**The question: is the composition failure fixable by prompt?** Pilot 8 finding
5 — run A's seat spent 36 deaths on `untilX` walking and never issued a single
`jumpAtX`, the same as pilot 7's run A, a 1-of-2 rate across two pilots. The
plan's transcript analysis said the option was never *retrieved* rather than
considered and rejected, so the rule was rewritten to fire on a death record the
seat has just read.

**Partly, and the partial answer is the informative one.** The rule converted
run A completely — 9 of its 14 moves carried `jumpAtX`, all paired with
`untilX`, four presses produced four take-offs, and it cleared the planet in
7m23s. It did not convert run B, which issued one composed move in 62 and aimed
it past the lip. The headline rate is still 1 of 2. What changed is the shape of
the miss, and that is a different problem than pilot 8 had.

## Composition, the primary measurement

| | pilot 7 run A | pilot 8 run A | **pilot 9 run A** | **pilot 9 run B** |
|---|---|---|---|---|
| `/move` calls | 25 | 60 | 14 | 62 |
| calls carrying `jumpAtX` | 0 | 0 | **9** | **1** |
| jump presses reaching the x | 0 | 0 | 4 | 1 |
| take-offs | 0 | 0 | **4** | 0 |
| clear | no | no | **yes** | no |

Run A's aims came from the rule as written. Its rc=3 death — a fall the sampler
placed and no `/move` reply reported — carried `lastStoodAt {644, 476}`, ground
height at the pit's near lip. The seat subtracted the taught margin and issued
`jumpAtX: 624` **six** times; three of those reached the x and pressed, at 632,
632 and 628 (a 4–8px overshoot, comfortably on the ledge). It issued
`jumpAtX: 816` three times, of which one reached the x — the clearing jump,
pressed at `{816, 429}`. The other five never got to press: two died at the
patrol before reaching the jump x (one of them a bare, un-armed move), one died
at the pit before reaching x=816, and two returned `arm-timeout` and never ran
at all. So the aim was right every time it was tested — **4 presses, 4
take-offs** — and most of the calls carrying it were spent on the coordination
around the jump rather than on the jump.

Run B's seat is the pathology the rule was written against, and the rule did not
stop it: 15 identical armed `untilX: 704` walks, 9 more armed at `untilX: 1100`,
9 bare at `untilX: 1100`. It walked into the same pit over and over — the same
lip run A jumped.

It composed exactly once, on its twelfth death:
`{arm: freeze, jumpAtX: 720, untilX: 820}`. That press was **refused**
(`arm-fired`, `jump-ignored`, `respawned`; `tookOff: false`, pressed at
`{720, 514}` — a y of 514 is already below standing height, so the astronaut was
falling when the key went down, which is exactly why the game ignored it).

The aim is the failure, and it has to be judged against what the seat held **at
the time**, not against the ledger's final state. Its last `/state` before the
aim handed `rc=[11,10,9,8,7,6,5,4,3,2]`, and the pit records in that hand read
`lastStoodAt` 648 (rc=4), 652 (rc=7), 656 (rc=9), 648 (rc=10), 652 (rc=11). So
the lip it had evidence for was 648–656, and `jumpAtX: 720` overshoots it by
64–72px where the rule asks for at least 20px the other way. The value 644
appears nowhere in run B's ledger before this move — the record that first names
it is rc=12, the death this very aim caused — so it is not part of the
explanation for the aim. The rule says "lip minus at least 20"; the seat used a
number on the wrong side of the lip entirely.

Three things the full table shows that a highlights version would hide. The 624
aim never changed across every jump the seat aimed at the first pit — moves 4,

varying it, which is a forgetting, not a re-aim. And the `untilX` tightened from
750 to 720 after the first crossing, which is PR #37's F3 fix (set `untilX`
*before* the landing spot, not past it) being read by a seat for the first time.

## What the sampler measured

One line per placed death in `logs/<RUNID>-laptop-driver.log`, so these are
counts. **The window matters this pilot**, and it is a limit the ledger has
always had rather than a new one: the ledger only sees a sampler death that some
`/state` drained. Run B's seat stopped calling `/state` after rc=17 and the run
was then killed, so its last 32 deaths have `/move` copies only and the
sampler's copies were still queued in the page at shutdown. Those 32 are not
measurable either way and are excluded rather than counted as misses.

| | run A (all 8) | run B (rc 1–17) | both | pilot 8 baseline |
|---|---|---|---|---|
| deaths | 8 | 17 | 25 | 43 |
| observed by the `/move` loop | 5 | 13 | 18 | 30 |
| observed by the sampler | 8 | 17 | **25** | 39 |
| **observed only by the sampler** | 3 | 4 | 7 | 12 |
| observed by neither | 0 | 0 | **0** | 1 |

Twenty-five of twenty-five placed, none missed, against pilot 8's 39 of 43 with
one seen by neither. That is the channel the `lastSeen` fix owns, and it is the
right direction — but 25 deaths is a small sample and run B's excluded tail is
exactly the busy, cluster-heavy stretch where the old blind window bit hardest.
Consistent with the fix; not proof of it.

Run B's unmeasurable tail also contains 8 respawn counts that appear on no
ledger line at all (rc 18, 22, 26, 30, 32, 40, 45, 48). Those are `/move`'s
limit, not the sampler's: a move breaks on the first respawn it notices and
reports one death, so a count that advances by two inside one move loses the
intermediate. Whether the sampler placed them is unknown — nothing drained it.

## `recentDeaths` — the records that used to fall on the floor

**Every sampler-only death reached a seat: 7 of 7** (3 in run A, 4 in run B),
against pilot 8's **3 of 12**. Run A's seat cited the feature by name in its
report's "What confused me" — "`lastDeath` vs `recentDeaths` indexing required
careful reading of `respawnCount` jumps to catch deaths that occurred during
unobserved moves" — which is a seat describing the mechanism working and finding
it fiddly, not a seat that missed it.

The mechanism is visible in run B's ledger doing the exact thing one slot could
not:

```
death rc=17 via=move    ...  kept=true  listed=true
death rc=15 via=sampler ...  kept=false listed=true      <- not the newest
state handed rc=[17,16,15,14,13,12,11,10,9,8]            <- delivered anyway
```

Under pilot 8's single slot, rc=15 arriving after rc=17 was correctly rejected
as stale and lost. It is now second in the list the seat reads. That is pilot
8's rc=27/rc=31 case, caught.

Run B also exercised the cap: 31 evictions across 49 deaths, each logged. Run A
had none (8 deaths, cap 10). The cap of 10 came from replaying pilot 8 run A's
ledger during review — its deepest drain is exactly 10 records, and the
originally shipped cap of 5 would have dropped rc=27 *inside the drain that
added it*.

## The digest is gone

**Binary, and it passed: zero digest markers in all four seats** — no
`ask_predecessor` tool, no predecessor/handoff/digest text, in either run's
laptop or phone transcript. Pilots 5, 6 and 7 reproduced the injection in every
seat. Run B's laptop is the strongest single case: 358 records, the longest seat
life any pilot has recorded, and not one of them is a digest turn.

One accuracy note the review caught (PR #37 F6) and this report owes: `-ne -e
<intercom>` subtracts **five** discovered extensions, not one. Besides `handoff`
the seats also lose four loose dev extensions in `.pi/extensions/`
(`import-repro.ts`, `prompt-url-widget.ts`, `redraws.ts`, `tps.ts`). None has a
model-visible surface in `-p` mode, so nothing here is attributed to them — but
the delta against the pilots 5–8 baseline is five extensions and the run-pilot
comment currently says one.

## Findings

1. **The trigger-bound rule converts a seat that two prior pilots could not**
   *(Fact — the pilot's question, half-answered)*. Run A issued 9 `jumpAtX`
   calls in 14 moves, against pilot 8 run A's zero in 60 and pilot 7 run A's
   zero, from the same seat role, model and level; it took off on 4 of 4 presses
   and cleared. The retrieval hypothesis behind the rule is supported here: the
   seat's aims are the rule's arithmetic applied to a record it had just read.

2. **It does not convert both seats, and the residual failure has a new shape**
   *(Fact — composition, still 1 of 2)*. Run B issued one composed move in 62
   and aimed it 64–72px past the lip its records at that moment supported
   (`lastStoodAt` 648–656 across rc=4/7/9/10/11). Pilots 7 and 8's non-composing
   seats never retrieved the option; this one retrieved it and mis-parameterised
   it. The next prompt touch is about the lip, not about reminding the seat to
   jump — and the review already drafted the fix (PR #37 F11: the sampler-scope
   check currently says "sits near where this fall started", which is circular,
   where "within ~150px of `diedAt.x` on the side you came from" is checkable).

3. **The take-off rate at the taught margin holds at 7 for 7** *(Fact)*. Pilot
   8's 3 of 3 plus pilot 9 run A's 4 of 4, against pilot 7's 1 of 5 at an 11px
   lead. Every press that used "lip minus at least 20" lifted; the one press
   that used a number past the lip did not. Two pilots, one rule, no
   counter-example yet.

4. **Every sampler-only death reached a seat** *(Fact — `recentDeaths`)*. 7 of
   7 against pilot 8's 3 of 12, with a ledger line showing a non-newest death
   delivered where one slot would have dropped it. The cap that makes this work
   was set from measurement during review, not chosen.

5. **The sampler placed every death in the measurable window** *(Fact, small
   sample)*. 25 of 25 with none seen by neither, against 39 of 43 and one. The
   `lastSeen` fix owns this channel, but run B's 32-death tail is excluded
   because nothing drained it, and that tail is the cluster-heavy stretch where
   the change should matter most. Consistent, not proven.

6. **The cross-run digest contamination is gone** *(Fact — binary)*. Zero
   markers in four seats across two runs, where pilots 5–7 reproduced it in
   every seat. Cross-run independence claims in this report are now honest in a
   way pilot 8's were not.

7. **The ledger cannot see a sampler death that nothing drained** *(New limit,
   found by this pilot)*. Run B's last 32 deaths are unmeasurable for sampler
   coverage because the seat stopped calling `/state` and the run was then
   killed. Pilot 8's table has the same conditioning and never showed it,
   because both its runs drained regularly. Any future coverage figure has to
   state its window; this one does.

8. **A 35-minute seat is a new regime, and the ceiling is now the binding
   constraint** *(Fact)*. Run B lived 34m46s over 358 records, against pilot 8
   run A's 19m17s over 300 — 1.8x the wall-clock on 1.2x the records, i.e. a
   seat that spent much more of its life waiting out backoffs and still kept
   playing. Surviving 21 429s means a seat no longer dies of rate limits, so
   what ends a run now is the orchestrator ceiling — the one ending under which
   no seat has ever written a report.

## Honesty caveats

- **Four changes moved at once**, and the report attributes nothing across
  channels. Composition is read from the move ledger (transcript `/move` tool
  calls); sampler coverage from the driver ledger's `via=` lines; `recentDeaths`
  reach from `state handed` lines cross-referenced against the ledger; the
  digest from seat startups. No claim here depends on two channels at once.
- **Reach is counted at delivery, not at insertion.** The `listed=` flag is
  decided when a record enters the list and a later eviction falsifies it — the
  adversarial review caught that this would over-report (34 `listed=true` against
  a 5-slot list in a replay of pilot 8). Every reach number above comes from
  `state handed rc=[…]` lines. Those lines cannot in general distinguish a
  laptop `/state` from a phone glance (the glance discards `recentDeaths`); in
  these two runs the phone driver never called the laptop driver at all, so the
  ambiguity does not bite here, and the figures were cross-referenced against the
  laptop transcripts regardless.
- **One clear in two runs is not a clear rate**, and this is the second clear in
  nine pilots. Run B did not clear and never tested the margin.
- **Armed moves are driver-reflex.** Run A's crossings rode `arm-fired` on
  freeze or platform; the driver owns the ~0.2s reaction, not the seat.
- **The driver solved every puzzle** (bands consistent with pilots 3–8).
- **Run B's seat and phone reports do not exist**, so this pilot's critique
  deliverable is half of pilot 8's. What run B contributes is behavioural data
  and notes, not a written seat critique.
- `diedAt`'s and `lastStoodAt`'s known biases apply unchanged (~14px sampling
  lag; `lastStoodAt` is the last *sampled* rest).
- **Nothing in the harness changed between run A and run B** — same merge, same
  build, same prompts. The two runs differ only in the seats' behaviour.
- **Every number in this report was re-derived from the artifacts by a
  zero-context reviewer across several rounds before publication, and each round
  corrected numbers — including numbers introduced by the previous round's
  fixes.** The first pass corrected both `/move` denominators, the pilot 8
  baseline, the `jumpAtX: 624` issue count, two endurance multipliers, the
  traced-crossing table, run B's lip evidence and two off-by-one tallies; later
  passes caught a pilot 7 baseline that the *first correction* had invented,
  sitting in the primary-measurement table. That is the reason this bullet does
  not say "it was checked": the correction passes needed checking too, and the
  round counts live in the mailbox rather than here, where they would go stale
  on the next commit. The load-bearing results — 25/25, 7/7, zero digest
  markers, the 429 table, the verified clear — survived every round unchanged.
