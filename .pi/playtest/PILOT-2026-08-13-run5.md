# Constellation co-op pilot, run 5 — planet-1, 2026-08-13

Two runs, back to back, against constellation `604a422` — the first co-op play
since the jump-outcome telemetry (PR #25) landed, and the first under the
arm-ordering protocol that pilot 4's finding 4 asked for (folded into the seat
prompts on this branch: the laptop's ask and armed `/move` go out in the same
turn, and the phone holds a freeze cast until its partner says they are
arming). Seats: laptop `google/gemini-3.5-flash-lite`, phone
`google/gemini-3.1-flash-lite`.

Run A `20260813-221712`: ~3m27s of play, 11 deaths, no clear.
Run B `20260813-223147`: ~1m54s of play, 8 deaths, no clear.
Both laptop seats were killed by the token-rate 429
(`GenerateContentInputTokensPerModelPerMinute-FreeTier`, 250k input
tokens/min), with `Please retry in 14.2s` and `11.6s` respectively. Times below
are UTC transcript stamps, following pilot 4's convention: driver observations
are tool-reply stamps, seat actions are tool-call stamps.

**The question this pilot exists to answer: do the new `jump` and
`lastStoodAt` fields change what a seat can reason about at the pit?** Pilot 4
ended on exactly this gap — two different jump failures produced identical
replies, so "the pair never tested the jump" — and the aim sweep then settled
the aim question offline. This is the first time live seats played with the
answer available to them.

**Yes — and the pilot produced two seat-issued jump verdicts, one per run,
both reasoned to the same aim.** Run A's laptop worked from `lastStoodAt` pit
data to a plan it announced as "I will jump across the pit at x=630", issued
`{jumpAtX: 630, untilX: 850}`, and got back `jump: {tookOff: true, pressedAt:
{x: 632, y: 476}, apexY: 363}` — a real take-off, verdict attached, from a
seat that could finally tell it happened. Run B's laptop, with no memory of
run A, derived the same 630 and jumped `{jumpAtX: 630, ms: 6000}` to the same
verdict. Pilot 4's central ambiguity (an attempted jump indistinguishable
from no jump) did not reproduce, twice. Both jumps failed the same way — the
aim was fine and the *release* was wrong: nothing cut the horizontal input
inside the flight, so both astronauts overflew the whole bridge and came down
past its far end, still over the pit. And the pair of failures bracket this
pilot's sharpest new finding: run A's overflight death was **invisible** (the
move had already returned when it landed — see "Deaths the driver cannot see"
below), while run B's was **fully captured** (`diedAt {896, 602}`,
`lastStoodAt {632, 476}`) — and the seat that could see it still misread it
as success ("Cleared the pit", finding 7).

## The jump — pilot 4's owed experiment, run live

The sequence, all driver-logged fields, run A:

- 03:20:38.301 the laptop announces: "Need one more Freeze Stars to reach
  x=564, then I will jump across the pit at x=630. Cast Freeze Stars, arming
  on freeze." The 630 is reasoned, not guessed: its three pit deaths to that
  point all carried `lastStoodAt` at x=644–648, ground height — the last spot
  it stood before falling — so it aimed just inside the nearest lip it had
  evidence for. (The true fall edge is x≈656; the aim sweep put the reasoned
  number well inside the workable band.)
- 03:20:42.129 the armed approach fires (`armedForMs` 559) and parks at
  x=576, enemy frozen — the two-stage plan run B of pilot 4 invented and
  never completed.
- 03:20:43.237 `{"dir":"right","jumpAtX":630,"untilX":850}`.
- 03:20:44.477 the reply: `events: ["jumped","reached-x"]`,
  `jump: {tookOff: true, pressedAt: {x: 632, y: 476}, apexY: 363}`, ending at
  x=852, y=459 — airborne, descending, past the bridge's far end (the bridge
  spans x≈722–818; past 818 there is still pit below).
- 03:20:45.633 the next `/state`: `respawnCount` 11 — dead — with `lastDeath`
  still the *previous* death (`respawnCount: 10`). The death the seat most
  needed to see has no record anywhere.

Two things are true at once. The telemetry did its job: `tookOff: true` told
the seat the aim was tested (pilot 4's runs never got that far), and
`pressedAt` pinned where. And the failure it revealed is precisely the aim
sweep's headline reproduced from the seat side — nothing released the run.
The sweep's 6-for-6 landings all carried an `untilX` *over the bridge*
(untilX 780); this seat chose 850, past the far gap, so the input never cut
and the arc carried over everything. Whether the astronaut grazed the bridge
on the way through cannot be told from the reply; what is certain is that at
the move's end it was at x=852 still descending, and one second later it was
dead with no site reported.

The laptop was killed by the 429 within seconds of that `/state`, so run A
ends there: one verdict-carrying jump, aimed right, released wrong, its death
unrecorded.

**Run B ran the second trial, and its death was captured.** In its final
minute (a segment corroborated by the phone's notes and the seat's own
intercom), the run B laptop diagnosed the stale platform out loud ("An old
platform is lingering, so arming on platform fires instantly and gets me
killed"), switched to freeze arms, and at 03:33:39.729 armed
`{jumpAtX: 630, ms: 6000}` — the same aim as run A, independently derived.
The reply (03:33:44.370): `events: ["arm-fired","jumped","respawned"]`,
`jump: {tookOff: true, pressedAt: {x: 632, y: 476}, apexY: 362}`,
`diedAt: {x: 896, y: 602}`, `lastStoodAt: {x: 632, y: 476}`. Because the move
was `ms`-bounded rather than ended by a `reached-x`, it was still running
when the fall completed — so this time the telemetry carried the whole story:
took off at 632, never rested anywhere past the takeoff point (no
bridge-height `lastStoodAt`), came down 78px past the bridge's far end.
Run A's open question — did the overflight touch the bridge? — is answered
for run B by the reply itself: it did not.

What the seat did with that reply is finding 7: it read "Cleared the pit but
died further ahead at x=896 in the dark zone" — success plus a new hazard —
when `lastStoodAt {632, 476}` says it never stood on anything past its own
takeoff point. The telemetry was present, complete, and misread.

The experiment the next session owes is narrower still: same park, same
jump, and a release *over the bridge* — the aim sweep's known-good pairing
(`jumpAtX` ≈ lip, `untilX` ≈ 780). Two live trials have now reproduced the
sweep's headline from the seat side — aim is not the variable, the release
is — and no live seat has yet issued the release that works.

## The protocol fix, measured

Pilot 4: three `arm-timeout`s across two runs, two of them ~90-second
double-blocked stalls, 27% of run B's playable life lost to one of them.
Pilot 5, with the finding-4 protocol in the prompts: **eighteen arms across
both runs (run A 11, run B 7), eighteen fired, zero timeouts, zero
deadlocks.** Every run-A ask and its armed `/move` went out in the same turn
(all ten ask→arm pairs ≤1.5s), and no freeze was ever cast against an absent
arm. Run B's laptop dropped the rule once: it asked "arming on platform —
cast Summon Platform when ready!" (03:32:26.954), ended that turn with no
arm and no `intercom_wait`, idled ~35 seconds until the phone's confirmation
woke it, and placed the arm at 03:33:01.984 — 21.8s after the cast had
landed. The arm fired in 62ms and the astronaut ran the patrol band
unprotected and died at x=384. The price comparison is the point: on a
freeze, that exact drift bought pilot 4 a 90-second double-blocked deadlock;
on a platform, whose wait is indefinite, it bought one unprotected run and a
third of a 114-second play window.
Run B's phone enforced the hold rule to the letter: asked "Could you cast
Illuminate or Freeze Stars? Let me know when you're ready" (03:32:12.251 — a
real ask, but without the word "arming"), it held — "Ready for either. Just
let me know when you're ARMED and which power you want" (03:32:15.709) — and
the laptop re-asked with "arming on freeze" 3.5s later. One round trip spent
on the missing word, cheap at this pair's 3-second cadence, expensive at the
1–3 minute cadence the prompts warn about; the prompts on this branch now
teach the laptop that "arming" is load-bearing for the phone, and give the
phone an explicit un-armed escape hatch, so the hold can't become the new
stall. The phone held again, correctly, at 03:33:07.300 ("Understood. Let me
know when you're ARMED and I'll cast freeze").

The freeze-armed rows bear it out: twelve freeze arms, `armedForMs`
497–2842, every one placed before its cast landed and fired into a live
window. The astronaut crossed the patrol band under every one of them.

**What replaced the deadlock is the already-standing platform.** Five of the
eighteen arms were `arm: {on: "platform"}` placed while a platform already
stood — four against one persisting from an earlier attempt (platforms now
persist indefinitely), one (run B's drift above) against its *own* requested
cast, landed 21.8s before the arm — so the level-based trigger fired in
60–64ms with no freeze up, and all five ended in a death (four in the patrol
band at x=312–428, one into the pit). Pilot 4
saw this once and correctly called instant-fire the *right* semantics for a
platform arm; what the pattern adds is that after the first platform cast of
a run, "arm on platform" can never again express coordination — the
condition is permanently true, so the arm is just "go now, unprotected", and
seats kept reaching for it as though it still meant "when my partner's cast
lands". Both run-A seats even diagnosed it in the moment ("Old platform
triggered immediate arm and enemy got me at 312") and then reached for it
again two minutes later. This sharpens the backlog's trigger-life item: the
freeze case wants `freezeMsLeft` so an instant fire can be told from a fresh
one, and the platform case wants the equivalent honesty — an `armedForMs` of
~60 on a platform arm means the trigger was already true when you armed.

## The 429 wall moved closer, because the fix worked

Both laptop seats died on the 250k input-tokens/min cap, like both pilot-4
runs — but faster: 3m27s and 1m54s of play against pilot 4's 3.5 and 5.5
minutes. The mechanism is visible in the turn cadence. Run A's laptop made
50 assistant turns in 3m27s (14.5/min; summed `input + cacheRead` 771k);
run B's made 33 in 1m54s (17.4/min; 398k). Pilot 4's laptops turned at
10.4–11.1/min. The protocol fix removed the 90-second stalls that were
pilot 4's only quota relief — its finding 7 noted the deadlocks were "the
only thing that kept either run alive as long as it was" — so a pair that
coordinates *better* now burns its token budget *sooner*. Run B compounds
it: launched one minute after run A's orchestrator ended, it also started
closer to a warm quota window and played the briskest of the four
pilot-4/5 runs — an average that *includes* the ~35s ask/arm idle gap
(finding 2's one drift), so its active stretches ran hotter than the
17.4/min suggests. The free-tier wall is now unambiguously the binding
constraint on live pilots: the backlog's token-rate-429 retryability item
(or paid-tier seats) is what buys the next pilot more than ~4 minutes.

Run B's phone deserves its own line: it served its partner's final request
(the laptop's last message, 03:33:48.165, asked for Illuminate; the cast
went out 0.8s later, into a game whose driver seat was about to die), then
sat through **five** consecutive 300s `intercom_wait`s — its own stop rule
says wrap after three — and was killed by the orchestrator's 1500s ceiling
before writing any report. Run A's phone stopped after ~10 minutes of
silence, probed once via the couch glance ("Partner, are you okay? Last
read shows 11 deaths"), and wrote a full report. The stop rule works when
followed; run B's phone report is the cost of not following it.

## Findings

1. **The jump verdict changes seat reasoning, live** *(Fact — the arc's
   question, answered)*. Both laptops independently derived the same aim
   (630) from `lastStoodAt` data, tested it, and received `tookOff: true`
   with `pressedAt` and `apexY`. Pilot 4's blocker — attempted and absent
   jumps returning identical replies — did not reproduce in either run. The
   remaining gaps are no longer feedback on the jump: they are feedback on
   the *release* (finding 3) and the seat's *reading* of a complete reply
   (finding 7).

2. **The arm-ordering protocol fix eliminated the deadlock class** *(Fact)*.
   18/18 arms fired, zero timeouts, zero double-blocked stalls, against
   pilot 4's 3 timeouts and two ~90s stalls. Cost: one round trip lost to a
   freeze ask that lacked the word "arming" (the phone held, per its new
   rule, until the laptop re-asked with it — 03:32:12–18); the prompts on
   this branch close that seam. Discipline was clean but not perfect: run
   A's laptop kept the same-turn rule on all ten ask→arm pairs and both
   phones held their rule throughout, while run B's laptop dropped it once —
   asked, idled ~35s, armed 21.8s after the cast landed, died at x=384. What
   the protocol change moved is the failure's *price*: cast-before-arm on a
   freeze used to buy a 90s deadlock; on a platform, whose wait is
   indefinite, the same drift bought one unprotected run.

3. **A death that completes between moves is invisible, and whether a jump
   death is visible currently depends on the move's terminator** *(Fact —
   new)*. Three of run A's eleven deaths — a `reached-x` that ended
   mid-fall, a freeze that lapsed while parked, and run A's jump — produced
   no `diedAt`/`lastStoodAt` anywhere: the `/move` had already returned, and
   `/state`'s `lastDeath` correctly goes stale-guarded rather than lying.
   Run B's jump is the control: `ms`-bounded, the move outlived the fall,
   and the same death arrived fully described. An `untilX` under the arc
   hides the outcome; an `ms` shows it — a distinction no seat can be
   expected to plan around. The freshness rule works; the data is simply
   absent, and it is absent precisely at moves that end at their target.
   *(Recommendation — harness)* The driver should keep capturing deaths
   while *no* move is running — a light idle sampler updating `lastDeath`,
   so the next `/state` can answer "where" instead of only "again". It
   observes; it does not act; the honesty split is untouched.

4. **An already-standing platform makes every platform arm an instant,
   unprotected "go"** *(Fact — pilot 4's single case, now systematic)*.
   Five platform arms placed while a platform stood, five instant fires
   (60–64ms), five deaths — four against a platform persisting from an
   earlier attempt, one against the seat's own cast that had landed 21.8s
   earlier during finding 2's ask/arm gap. With platforms persisting
   indefinitely, the platform trigger is permanently true after the run's
   first cast, and seats kept using it as though it still meant "when the
   cast lands". *(Recommendation)* The trigger-life backlog item
   covers the diagnosis side (`freezeMsLeft`, and the platform equivalent);
   the prompt side could teach "check `platformCount` before arming on
   platform — if one is standing, the arm fires immediately and buys you
   nothing", the same way it teaches the freeze protocol now.

5. **Better coordination shortened the runs** *(Fact — harness/pi, not the
   game)*. Turn cadence rose ~40–70% over pilot 4 once the stalls were
   gone (run B's average includes finding 2's ~35s idle gap, so its active
   stretches ran hotter still), and both laptops hit the 250k
   input-tokens/min cap sooner (3m27s, 1m54s). Live co-op is now bounded by the free tier, not by the pair's
   play. The token-rate-429 retryability item (BACKLOG Active — referenced
   by title; numbers shift) is the unblock; until then, pilots should
   space runs by several minutes and expect ~2–4 minutes of play.

6. **The support seat's feedback ask survives with the glance answering
   part of it** *(Fact — consistent with pilot 4's finding 6)*. Run A's
   phone used `worldLastDeath` correctly and immediately ("Caught the death
   — looks like you were near 328", 03:17:47, quoting the death site, not
   the respawn point), and its report still asks for the same thing on the
   phone screen itself: platform placement and jump-failure feedback that a
   pair in separate rooms would not have. The game-UI finding stands; the
   glance is a harness affordance and was labeled as such.

7. **A complete death reply can still be misread — `lastStoodAt` needs
   teaching, not more fields** *(Fact — new)*. Run B's laptop received the
   pilot's most complete death record — `tookOff: true`,
   `diedAt {896, 602}`, `lastStoodAt {632, 476}` — and told its partner
   "Cleared the pit but died further ahead at x=896 in the dark zone." It
   had not cleared anything: `lastStoodAt` at its own takeoff point means it
   never stood on a single surface past x=632, and the y=602 death is the
   same falling class as every other pit death. The seat read distance as
   progress. The prompt teaches what `lastStoodAt` *is*; what this misread
   shows is the inference it licenses being run backwards — "died far away,
   so I got far" — when the field's whole point is that only a *rest*
   proves arrival. *(Recommendation — prompts, next pilot)* One line in the
   laptop prompt: "a death past the pit with `lastStoodAt` still at or
   before the lip means you never landed anywhere — you overflew or fell;
   only a `lastStoodAt` on the far side or at bridge height means you got
   across."

## Honesty caveats

- **Armed moves are driver-reflex.** Every patrol-band crossing in both
  runs rode an armed move; the seats chose maneuvers and triggers, the
  driver held and fired them. The 18/18 figure in finding 2 is armed-move
  progress and should be read with that discount.
- **The driver solved every puzzle.** Phone seats chose which power and
  when; solve times (freeze ~0.67s, platform ~4.85s, illuminate ~0.2s) are
  driver mechanics, consistent with pilots 3–4's bands.
- **The couch glance is a harness affordance, not a game feature.** Both
  phone-seat death citations came from `worldLastDeath`; the phone screen
  shows none of it.
- **Both runs are truncated; neither laptop report was written** — the 429
  killed both seats before that step, so laptop-side claims come from their
  notes files, intercom traffic, and the session transcripts. Run B's phone
  report was never written (killed at the orchestrator ceiling mid-wait);
  run A's phone report exists and is quoted above.
- **Death counts are not a quality metric** across runs of different
  lengths and interventions.
- The jump analysis rests on two trials — one per run, same aim, different
  terminators, no `untilX`-over-the-bridge trial yet. `diedAt`'s known
  biases (one-poll lag, fall-registration offset) apply to every table row;
  `reports/video/20260813-221712/laptop.webm` and
  `reports/video/20260813-223147/laptop.webm` are the way to falsify the
  overflight readings.
