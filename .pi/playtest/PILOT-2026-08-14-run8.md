# Constellation co-op pilot, run 8 — planet-1, 2026-08-14

Two runs against constellation `604a422` — the same build pilot 7 ran, so the
game is unchanged between the two pilots. Seats: laptop
`google/gemini-3.5-flash-lite`, phone `google/gemini-3.1-flash-lite`. Two
harness changes shipped into this pilot: the **death sampler** (a record for the
falls no `/move` is there to see) and the **aim-margin** technique line in the
laptop prompt. Both landed in the same commit, and the caveat that implies is in
"Honesty caveats".

Run A `20260814-200144`: 19m17s of play, 36 deaths, no clear.
Run B `20260814-202158`: 7m46s of play, 7 deaths, **cleared planet-1**.

Neither run was ended by a 429 or by the orchestrator ceiling. Both seats in
both runs stopped on their own and wrote their reports — four for four. Times
below are UTC transcript stamps, pilot 4's convention.

**The question: does a taught aim margin, on top of pilot 7's demonstrated
pairing, put a seat on the bridge?**

**Yes — and it cleared the planet.** Run B is the first live co-op clear in
eight pilots; every prior pilot report records "no clear". The answer is not
just that the margin worked but *how* it got its number, which is the other
half of this pilot: the aim came from a death the sampler placed and no `/move`
reply ever mentioned.

The twelve sampler-only deaths are the between-moves class — pilot 7 had four

correctly, and one of them is the aim that cleared the planet.

The two observers also cross-check each other. On the deaths both saw, the
sampler's independently-sampled `diedAt` agreed with `/move`'s to within a poll
— run A rc=1 `372,476` (move) vs `376,476` (sampler), rc=2 `460,476` vs
`452,476`; run B rc=1 `268` vs `264`, rc=3 `344` vs `340`, rc=5 `420,476` vs
`420,476` exactly. That is the first check on `diedAt` that is not the aim
sweep's trajectory trace.

The ledger also caught a defect in the harness change itself. Run B's rc=7 —
the death at row 11 above — was reported by `/move` with **no** `lastStoodAt`,
because the astronaut left the bridge inside that move's first samples. The
sampler, whose history spans the life rather than the move, had it standing on
the bridge at `{800, 429}`. The tie-break as shipped for this pilot preferred
the move's copy unconditionally, so the seat kept the record that could not say
what was fallen off and lost the one that could — on exactly the
bridge-vs-never-got-there question `lastStoodAt` exists to answer. The rule now
prefers whichever copy names `lastStoodAt`, falling back to the move's when both
are equally informative. **That fix postdates both runs**; everything measured
here ran on the naive rule.

## What the sampler did NOT reach, and why

Of the twelve sampler-only deaths, only three ever reached a seat. `lastDeath`
is one slot holding the newest death, and it is drained on `/state`: a seat that
does not look promptly loses the intermediate records. Run A's tail is the clean
example — the sampler observed rc=27 and rc=31, but by the time a `/state`
drained them a later `/move` had already recorded a higher count, so both were
correctly rejected as stale and the seat never learned them.

This is a design consequence, not a defect: for the question the seat actually
asks — "did the move I just made kill me?" — the newest record is the right
answer, and the prompt now tells it to look after any move ending below standing
height. Run A's seat received nine non-null `lastDeath` records over the run and
caught two of its ten sampler-only deaths that way. The follow-up is a short
`recentDeaths` list rather than a single slot (added to BACKLOG).

One death in run A (rc=35) was seen by neither observer, in a cluster of four
deaths (rc 33–36) that the sampler missed entirely while `/move` caught three.
The sampler clears its history after each death and needs a fresh sample before
it can place the next one, so deaths arriving within about two polls of each
other fall outside it. Stated as an observed limit; the mechanism is consistent
with the code but not separately instrumented.

## The 429 no longer ends a run

Run A's laptop took **thirteen 429s and survived all thirteen** — twelve
`GenerateContentInputTokensPerModelPerMinute-FreeTier`, one request-rate, zero
per-day, with stated delays from 13.3s to 58.8s. Run B took four, all
token-rate. A single 429 of that shape used to kill a seat outright — four of
them across earlier pilots, pilot 7's two laptops being the most recent. This is
PR #30 measured in live play.

It is also why all four seats wrote reports. Pilot 7's finding 6 observed that
no seat had ever written one when a run ends by 429 or ceiling, across eight
seats. Neither run 8 ended either way: run B won, and run A's seat wrapped up
on its own after 36 deaths ("Playtest complete!" is how its final turn opens;
which of the prompt's stop conditions it judged itself against, it does not
say). The orchestrator ceiling was raised to 2100s for this pilot precisely so
a seat that decides to stop at its prompt's 25-minute mark has room to write —
in the event neither run came close to it, so the ceiling was not the operative
cause; surviving the 429 was.

Intercom coordination was quiet. Run B recorded **zero** `arm-timeout`s across
7 `arm-fired`s; run A recorded 3 across 23. Pilot 7 had 4 in run B alone, 3 of
them manufactured by the wait-start boundary bug that PR #29 fixed.

## Findings

1. **The taught margin converts the pairing into a landing** *(Fact — the
   pilot's question, answered)*. Three `jumpAtX: 630` presses against a lip at
   652, three take-offs, landing on the bridge and then clearing from it.
   Pilot 7's five presses at 645 produced one take-off. The rule that did the
   work is "at least 20px before the edge", and the reason it is needed is that
   two biases push the same way: the press lands up to ~15px late, and the
   `lastStoodAt` the edge is derived from is itself sampled before the astronaut
   left.

2. **The sampler's record is what the margin was applied to** *(Fact — the two
   changes composed)*. The lip at 652 came from a death that no `/move` reply
   reported. Without the sampler the seat would have had `respawnCount` 4 and a
   respawn position of x=80, which is the exact artefact `diedAt` exists to
   defeat. The chain is: invisible death → placed record → correct lip → 22px
   margin → take-off → clear.

3. **The misread survives where the record does not reach the seat, and once
   where it did** *(Fact + open)*. Run A's seat received the rc=11 sampler
   record and reasoned it correctly and unprompted — "lastStoodAt (644, 476) are
   the last known stable ground... a gap or pit exists between these two points"
   — then messaged its partner "Found a pit at x=644". On rc=12
   (`lastStoodAt {656, 476}`) the same seat wrote "Crossed first pit
   (lastStoodAt x=656)" in its notes and "successfully crossing the first pit"
   in its report. Both lips of a pit are ground height, so `lastStoodAt.y`
   cannot separate near lip from far lip — only x can, against a pit edge the
   seat has to remember. Pilot 7 could say every misread lived in the no-record
   path; that is no longer true, and the remaining case is narrower and
   specific.

4. **Both seats now produce real game critique** *(Fact — the deliverable)*.
   Four reports, and the content is about the game rather than the harness: both
   phone seats independently flagged the pacing imbalance between Summon
   Platform's tap sequence (~4.8–4.9s) and Freeze Stars' quick math (~0.7s), and
   both laptop seats asked for pit-edge and patrol-boundary telegraphing. Run
   B's phone seat also volunteered the couch-glance caveat itself — "I had to
   rely on the `world` glance, which the player in another room wouldn't have" —
   which is DESIGN.md's own stated limit, reached from the seat side.

5. **Run A never issued a single `jumpAtX`** *(Fact — composition, unchanged)*.
   Same prompt, same teaching, and it spent 36 deaths and 19 minutes on `untilX`
   walking (18 calls at 630, 3 at 650). Pilot 7's run A did the same thing. One
   prompt line still does not force the composition in both seats; the rate is
   one in two across two pilots.

6. **Harness catch: the tie-break threw away the better record** *(Fact —
   fixed post-run)*. Run B's rc=7 had a `/move` copy with no `lastStoodAt` and a
   sampler copy naming the bridge at `{800, 429}`; the shipped rule preferred
   the move's unconditionally. Found in the driver ledger this pilot added, not
   by reading the code. Now prefers whichever copy names `lastStoodAt`.

## Honesty caveats

- **Two changes moved at once.** The clear cannot be attributed to the aim
  margin alone: the sampler supplied the number the margin was applied to. What
  is separable is the take-off rate — 3/3 at a 22px lead vs pilot 7's 1/5 at an
  11px lead, same game build, same lip — and the death counts, which are
  driver-logged.
- **Armed moves are driver-reflex.** Every crossing in run B rode one
  (`arm-fired` on freeze or platform); the clear itself was platform-armed. The
  driver owns the ~0.2s reaction, not the seat.
- **The driver solved every puzzle** (bands consistent with pilots 3–7).
- **One run, one clear.** Run A did not clear and never tested the margin. A
  single clear is not a clear rate.
- `diedAt`'s and `lastStoodAt`'s known biases apply to the sampler exactly as
  they do to `/move` — it is the same rule at the same 60ms cadence.
- **Two prompt lines changed after the runs**, in review: the `jump-ignored`
  bullet now excludes the case where the same move also reported a death, and
  both prompts now teach that `/state`'s `lastStoodAt` is scoped to the life
  rather than the move. Neither was exercised by either run — run B's three
  presses all took off and run A never jumped — but the seats that produced
  these numbers read the earlier wording. The 20px margin rule itself is
  unchanged.
- Run B's clear is verified independently of the seat's report: the transcript
  carries a `/move` reply with `events: ["arm-fired","jumped","won"]` and
  `state.won: true` at x=892, rc 7.
