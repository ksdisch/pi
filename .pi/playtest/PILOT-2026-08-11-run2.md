# Constellation co-op pilot, run 2 — planet-1, 2026-08-11

Run `20260811-172159`. Seats: laptop `google/gemini-3.5-flash-lite`, phone
`google/gemini-3.1-flash-lite`, both on **pi's stock retry defaults** — no
`.pi/settings.json` override, which is the point of this run. ~18 minutes,
**11 deaths, no clear**, both seats wrote their own report and stopped
voluntarily.

Run 1 (`20260811-123800`) is `PILOT-2026-08-11.md`; read that one first for the
game critique, most of which this run reproduces rather than replaces.

## What this run was testing

Run 1's players died mid-session on Google per-minute 429s. The harness branch
fixed the classifier (per-minute request-rate quotas are retryable) but the
default `2s/4s/8s` backoff still put its last attempt at t=14s — inside a
throttle window Google states as 25s+. This run asks whether the follow-up fix
(floor the backoff at the delay the provider states) survives real throttling
on stock defaults.

**It does, and the run proves it directly.** The laptop seat hit three real
per-minute 429s and survived all three:

| Google's stated delay | Predicted floor (stated + 1s pad) | Measured gap to next event | Old ladder would have given |
|---|---|---|---|
| 30.694s | 31.7s | **32.6s** | 14s → fail |
| 18.853s | 19.9s | **20.1s** | 14s → fail |
| 58.758s | 59.8s | **61.3s** | 14s → fail |

All three carried `GenerateRequestsPerMinutePerProjectPerModel-FreeTier`. Under
the shipped defaults this branch inherited, every one of them would have burned
its whole retry budget inside the window and killed the seat — the exact failure
that ended run 1. The measured gaps include the retried request's own latency,
which is why they sit slightly above the predicted floor.

**One of them nearly hit the ceiling.** The 58.758s delay floors to 59.8s
against a `MAX_SERVER_RETRY_DELAY_MS` of 60s — 0.2s of headroom. A stated delay
above ~59s would be clamped and would under-wait, reintroducing run 1's failure
in a narrower band. The clamp exists so a malformed value can't stall a turn
forever, but 60s is evidently not far above what Google actually asks for on a
free tier. Worth revisiting.

## Did the pair play better?

Deaths fell from **25 to 11**, and the seats stopped by choice with reports
written rather than being killed off. The coordination was also visibly better:
the laptop invented a sync protocol mid-run —

> **laptop:** Let's sync: I'll move to x=300 first. Then I'll say 'GO', you cast Freeze Stars instantly, and I'll sprint past!
> **phone:** Copy that. Ready for your 'GO' on freeze-stars. Watching for your cue.

— which is a human thing to do and did not happen in run 1. It still wasn't
enough: the cue-to-cast round trip is bounded by an LLM turn (~12s+), and the
freeze lasts ~3s.

Neither run cleared. `verify-rails.sh` clears planet-1 on attempt 1 with the same
drivers, so the level is beatable through this interface; what neither pair could
beat is the latency budget.

## Findings

1. **The 3s/5s power windows are unplayable at chat latency** *(Fact — both
   seats, both runs, top pain)*. This is run 1's finding #1 reproduced exactly,
   now with a second independent pair naming it unprompted. Laptop: "any slight
   delay in chat acknowledgment or movement execution resulted in failure."
   Phone: "it was sometimes unclear if my cast was successful in time."

2. **Standing still is lethal, so waiting for your partner is lethal**
   *(Fact — the dominant death cause)*. Laptop: "stopping anywhere outside spawn
   while waiting for a reply invariably led to death from patrolling enemies."
   The game punishes exactly the behavior co-op requires. *(Recommendation)* The
   laptop seat's own first ask — a safe hold or pause while a partner solves — is
   the single highest-value change, and it is the same conclusion run 1 reached
   from different words.

3. **The phone can't see whether it helped** *(Fact)*. The phone's only feedback
   is its own cast-feedback card; it has no view of the platformer. Its ask was
   "a status indicator for the partner to see when a power is being prepped."
   Run 1 asked for the mirror of this. Both directions of the co-op link are
   blind.

4. **The phone reported a clear that did not happen** *(Fact, and a caution about
   this harness)*. Its final intercom message was "Cleared! Great playing with
   you," and its report says "Partner reported done." No `won:true` was ever
   observed, and the laptop's own notes end at 11 deaths with an explicit
   decision to stop. A seat with no visibility into the win condition asserted
   the win condition. Treat per-seat reports as experience reports, never as
   outcome records — outcomes come from driver state.

5. **Puzzle pacing, from the seat that ran them** *(Fact)*. Illuminate/Trivia
   ~0.2s, Freeze Stars/QuickMath ~0.7s, Summon Platform/TapSequence ~4.8s. The
   phone called TapSequence "a bit stressful compared to the others, but very
   satisfying." That 7× spread between the cheapest and dearest power is a real
   design lever: the power that takes longest to earn is also the one whose
   effect expires while you earn it.

## Honesty caveats

- **The driver solved every puzzle**, not the phone player. The phone chose which
  power and when, and critiqued from the transcript; QuickMath is computed,
  Trivia answers come from the page's own question pool, TapSequence is observed
  and repeated. The phone's own report labels this correctly.
- Headless, so neither seat saw pixels. All perception is via driver state.
- One run, one planet, two seats. Deaths 25 → 11 across two runs is not a
  measurement; the retry evidence in the table above is, because it is read from
  timestamps rather than inferred from outcomes.

## Watching a run

- `HEADED=1 ./run-pilot.sh` opens real Chromium windows (game 960×600, phone
  390×720) so you can watch live. Nothing else changes.
- Every run records video regardless, to
  `reports/video/<RUNID>/{laptop,phone}.webm` — this run's are ~13 MB each.
  Playwright finalizes them at `/shutdown`, so they appear when the run ends.
  (Git-ignored, like all of `reports/`.)
- Live text view while a run is in flight: the intercom channel files at
  `.pi/intercom/playtest-<RUNID>/*.json`. Session logs stay buffered until exit
  and show only each seat's final message.
